# Cognitive Forensics: Bounding and Auditing Agentic Execution

**Status:** DRAFT
**Version:** 1.1
**Source spec:** [truth-root.md](truth-root.md), [grace-contract.md](grace-contract.md)

## Abstract

This document defines the architectural specification for **Cognitive Forensics** within the ecr-wg environment. When an autonomous agent executes a work product, the system must generate a tamper-evident audit trail that allows an operator or a forensics team to reconstruct, isolate, and verify the execution.

We reject the naive assumption that LLM outputs can be perfectly replicated. Instead, we establish a tripartite division of execution boundaries—the Permitted, the Possible, and the Probable—and define the cryptographic binding between Agent Enrollment Cards, EMILIA Protocol (EP) Action-Control Manifests, and the output Signature Blocks.

## 1. The Forensics Triad

Verifying or auditing an agentic event requires separating deterministic constraints from probabilistic behaviors. We define three distinct operational tiers:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          THE FORENSICS TRIAD                            │
├─────────────────────────────────────────────────────────────────────────┤
│  1. THE PERMITTED  │ Cryptographic & Deterministic │ EMILIA Receipts    │
├────────────────────┼───────────────────────────────┼────────────────────┤
│  2. THE POSSIBLE   │ Structural & Environmental    │ Sandboxes / MACs   │
├────────────────────┼───────────────────────────────┼────────────────────┤
│  3. THE PROBABLE   │ Distributional & Stochastic   │ Model Inference    │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.1 The Permitted (Deterministic / Cryptographic)
*   **Definition:** What the agent was explicitly authorized to do at the exact moment of execution.
*   **Enforcement:** Cryptographically frozen by the EMILIA Protocol (`EP-RECEIPT-v1`).
*   **Forensic Properties:** 100% reproducible. The receipt states the exact action, the target bytes (via Merkle anchors/digests), the authorization authority, and the time boundary. You do not need to re-run the model to prove authorization.

### 1.2 The Possible (Structural / Environmental)
*   **Definition:** What the agent was physically capable of doing based on the operating system, network routing, and file system permissions.
*   **Enforcement:** Bounded by OS sandboxing, directory isolation, read-only mounts, and the `EP-ACTION-CONTROL-MANIFEST` (`agent-action-control.json`).
*   **Forensic Properties:** **Reproducible given a pinned environment.** To achieve full reproducibility, the structural environment itself must be pinned. The audit trail must record the environment configuration (container image digest, mount configuration, and network policy).

### 1.3 The Probable (Distributional / Stochastic)
*   **Definition:** The actual cognitive reasoning and text generated by the LLM substrate.
*   **Enforcement:** Guided by Layer 1 (Substrate Physics) and Layer 3 (Persona Overlays).
*   **Forensic Properties:** **Non-deterministic.** Silent provider updates, hardware float non-determinism, GPU driver variations, and sampling temperature mean the exact token sequence cannot be guaranteed on a re-run. Forensics must treat this as a *probability distribution* over $N$ runs, rather than a single static value. We reconstruct the *input boundary* exactly, but characterize the *output* as a distribution.

## 2. Card-to-Manifest Cryptographic Binding

To prevent identity spoofing and scope creep, an agent's public enrollment card must cryptographically bind the agent's identity to its authorized operational envelope.

### 2.1 Canonical Manifest Serialization
To prevent whitespace discrepancies and semantic drift between identical manifests, the manifest digest MUST be computed over JCS-canonicalized bytes (JSON Canonicalization Schema / RFC 8785) of the `agent-action-control.json` file. One rule everywhere: digest canonical bytes, never raw files.

### 2.2 The Agent Action-Control Manifest
Located in the repo's `/.well-known/` directory or referenced by URI, this file declares the agent's authorized scope using machine-readable contracts:

```json
{
  "manifest_version": "EP-ACTION-CONTROL-MANIFEST-v1",
  "agent_id": "E-4B7E4B91-1849-001",
  "scopes": [
    {
      "action": "git_commit",
      "consequential": true,
      "assurance_tier": "CF-1",
      "paths_allowed": ["/enrollments/*", "/planning/*", "/specs/*"],
      "args_allowlist": ["-m", "--amend", "add"]
    }
  ]
}
```

## 3. The Forensic Signature Block

Every work product produced by an enrolled agent must carry a self-contained, tamper-evident signature block. This block serves as the "packing slip" that a forensics team extracts to verify or replay the event.

### 3.1 Slips as a Causal Chain
To prove the sequential execution of actions without relying on volatile wall-clock synchronization, signature blocks are chained. Each block includes a `prev_output_digest` pointing to the cryptographic hash of the prior action's output. Causal order is built directly into the chain.

### 3.2 Decoupled Authorization Receipts
Rather than embedding the full, volatile EMILIA receipt in the signature block, the block carries the `receipt_payload_digest`. This decouples verification, allowing the same receipt to anchor cleanly into SCITT, the forensic slip, and the local evidence chain without data drift.

## 4. Custody vs. Authorship

We establish a clear boundary between custody (who signed) and authorship (who generated).
*   **GPG Commit Signatures Prove Custody:** A git signature proves only that the registrant's key signed the commit; it cannot prove which model generated the tokens.
*   **The Two-Tier Identity Integration:** 
    *   **Seat:** The long-lived, enrolled identity on the card (the platform).
    *   **Body:** Binds the transient model substrate using EMILIA’s `agent_binding` delegation (`scheme`, `ref`, `observed_at`) + the `model_version_id` declared in the forensic slip.

---

## 5. Verification and Reconstruction Loop
When an auditor extracts this block, they can run a static verification pass without invoking an LLM:

1.  **Validate the Receipt:** Verify the `receipt_payload_digest` against the SCITT transparency log or offline EP receipt store. This proves the action was cryptographically authorized.
2.  **Verify the Manifest & Environment:** Fetch the manifest and container environment matching the `manifest_digest` and `environment_digest`.
3.  **Confirm Input/Output Integrity:** Recompute the SHA256 hashes of the files read during the session and compare them to `input_context_digest` and `output_digest`.

If the static verification passes, the audit trail is valid. The team can then proceed to rebuild the container matching the `environment_digest` to perform stochastic analysis of the reasoning layer.
